# BeepClean

Upload a video, get one back with the curse words beeped out and curse words in
on-screen text (subtitles, overlays) blurred.

- **Speech** is transcribed with Whisper (`faster-whisper`), and every flagged word
  is replaced by a clean sine beep. Censored spellings like `f***ing` count too.
- **On-screen text** is read with RapidOCR (PP-OCRv6) and the matching regions are
  blurred, pixelated, or blacked out.
- Nothing is uploaded anywhere. The whole thing runs locally on this machine.

## Run it

```bash
./run.sh
```

Then open <http://localhost:8000>.

The first run builds a Python virtualenv and downloads the libraries, which takes a
few minutes. It is done once. Set `PORT` to use a different port:

```bash
PORT=9000 ./run.sh
```

### Work on a real file

```bash
./try.sh ~/Videos/clip.mp4                     # beep + blur, writes out/clip-beeped.mp4
./try.sh ~/Videos/clip.mp4 --report-only       # just list what it found, change nothing
./try.sh ~/Videos/clip.mp4 --report-only --no-ocr   # speech only, much faster
./try.sh ~/Videos/clip.mp4 --model base.en     # more accurate, slower
./try.sh ~/Videos/clip.mp4 --blur blackout     # or pixelate
./try.sh ~/Videos/clip.mp4 --ocr-band 0.9      # scan more of the frame
./try.sh --help
```

`--report-only` is the quickest way to check whether detection is working, because it
skips re-encoding. Then drop the flag to produce the real file.

### What to look for in the output

```
  0:07.1 -> 0:07.8  fucking            confidence 0.71
```

Every hit is listed with the timestamps it occupies. `0:07.1 -> 0:07.8` means the
audio was replaced with a beep from 7.1s to 7.8s. Low `confidence` means the speech
recogniser was unsure of that word, so a miss there is likely a false negative. When
there is nothing to change the report says so and the file is copied untouched.

To confirm the beep by ear, open the result and listen at the listed time:

```bash
xdg-open out/clip-beeped.mp4
```

## How it works

```
upload -> probe -> transcribe speech -> read on-screen text -> beep + blur -> remux
```

1. **Probe** reads duration, resolution, frame rate and which streams exist.
2. **Transcribe** runs Whisper with word-level timestamps. Voice activity detection
   is on, which is what stops it inventing words during silence.
3. **Match** normalises each word (lower case, strips punctuation, folds leetspeak
   like `sh1t` or `a$$`, allows repeated letters like `fuuuuck`) and looks it up in
   `data/wordlist.json`. Matching is on whole words with a generated suffix rule, so
   `class`, `bass`, `hello`, `analyst` and `cumulative` are not flagged, while
   `shits`, `fucking` and `asses` are.

   Captions and speech are often censored, so `F*CK`, `f_ck`, `f**k`, `f***ing`,
   `sh*t`, `b_tch` and `f_ucks` are all matched. Arithmetic, `C#`, `a *= 2`,
   `snake_case` and words like `f**king` are not.
4. **Read on-screen text** samples frames near the bottom of the picture, runs OCR,
   and links detections into tracks over time. A track only becomes a hit if its
   text is actually profane, so ordinary subtitles are left alone.
5. **Render** only touches what changed. If only words were spoken the video track
   is copied untouched; if only subtitles matched the audio is copied untouched; if
   nothing matched the file is remuxed as-is. With no changes at all there is zero
   quality loss.

## Settings

Everything in `data/settings.json` is editable in the browser under **Settings**.

| Setting | Default | Notes |
|---|---|---|
| `model` | `tiny.en` | `base.en` and `small.en` are more accurate and slower |
| `vad_threshold` | `0.2` | voice-activity sensitivity. Lower catches quieter speech, but below ~0.15 it stops filtering silence and invents words |
| `beam_size` | `5` | larger is more accurate and slower |
| `condition_on_previous_text` | `true` | give Whisper the previous line as context |
| `beep_freq` | `1000.0` | beep pitch in Hz |
| `beep_amplitude` | `0.55` | beep loudness, 0 to 1 |
| `beep_min_ms` / `beep_max_ms` | `120` / `600` | a long word is capped at 600 ms of beep |
| `blur_mode` | `blur` | or `pixelate`, `blackout`. The effect scales with the caption size, so it hides text just as well at 4K as at 360p |
| `ocr_enabled` | `true` | set `false` for audio only, which is much faster |
| `ocr_fps` | `3.0` | how often frames are read. Raise to catch subtitle tails more tightly |
| `ocr_band` | `0.30` | fraction of the frame height scanned, from the bottom |
| `max_resolution` | `1080` | caps the short side of the output |
| `min_confidence` | `0.0` | raise to `0.6` to only beep words Whisper is sure about |
| `report_only` | `false` | `true` lists what was found but changes nothing |

## Word list

`data/wordlist.json` has three parts, all editable in the browser:

- `stems` - base words. Plurals and endings are generated, so `fuck` also catches
  `fucking`, `fucked`, `fucks`, `fucker`.
- `extra` - whole phrases that must match exactly.
- `allow` - words that are never flagged, whatever the stems say. This is the escape
  hatch for false positives.

## Live streams

Same filtering, applied while a stream is running.

```bash
# try it with no stream setup at all: a local file played as if it were live
./try.sh --simulate samples/1-subtitle-curse.mp4 --paced

# a real stream: pull from one RTMP endpoint, push the filtered result to another
./try.sh --rtmp-in rtmp://live.twitch.tv/app/STREAM_KEY \
         --rtmp-out rtmp://a.relay/APP/STREAM_KEY
```

`--paced` waits in real time so you can watch it behave like a live feed. `--fast`
(the default for local files) runs as fast as the CPU allows, which is what you
want for testing.

### How it works

The stream is cut into windows. Each window is analysed, edited, then emitted, so
the output trails the input by a predictable amount instead of drifting:

1. frames are decoded and the lower band of each frame is OCR'd on a timer
2. audio for the window is transcribed with Whisper
3. both decisions are applied, then the window is encoded and pushed

Detections carry across window boundaries, so a caption that straddles two windows
is still caught.

### What it costs you

This is the important part. The analysis is not free, and the delay is real:

| Setting | Delay added | Notes |
|---|---|---|
| Blur on-screen text only | about 1s | the fast path |
| Blur + beep speech | about 7 to 13s | roughly one window plus processing |

That speech delay is not a bug you can tune away. Whisper needs about 0.65x realtime
just for the audio, so a speech-filtered stream runs behind by design. It is fine if
you plan for a moderation delay, and wrong if you need to talk to people in real
time.

The window is 6 seconds by default because 4 second windows miss words. Measured on
a clip where the curse word sits at 12.0s:

```
  4s window   3.64s   caught=False   'as a country where we speak English.'
  6s window   4.09s   caught=True    'as a country where we speak English. Fuck you!'
  8s window   3.32s   caught=True    'as a country where we speak English. Fuck you!'
```

### Can it keep up?

Measured on this machine, 4 CPU cores and no GPU, blurring only:

| Stream size | Throughput | Result |
|---|---|---|
| 640x360 | 0.98x realtime | keeps up, about 0.8s behind |
| 1280x720 | 0.61x realtime | falls behind |
| 1920x1080 | 0.49x realtime | falls behind |

Adding speech takes it to roughly 0.28x realtime at 1080p. **So on this hardware
only 360p visual filtering runs in real time.** For a real 720p or 1080p stream you
need a faster machine or a GPU, and I could not test that here.

Rather than buffering forever when it cannot keep up, it drops the analysis for a
window and passes the video through unfiltered, so the stream keeps flowing at the
cost of missing a word occasionally. You will see `degraded` in the summary.

Useful flags:

```bash
--no-speech          # blur only, the fast path
--no-visual          # beeps only
--window 8           # longer windows, better speech accuracy, more delay
--max-height 480     # downscale to save encode time
--ocr-interval 0.5   # sample frames more often, catches short captions
--ocr-band 0.5       # scan more of the frame for text
--preset ultrafast   # default, needed to keep up
```

## Performance on this machine

No GPU, 4 CPU cores. Roughly, for a 1 minute clip:

| Stage | Time |
|---|---|
| Speech (`tiny.en`) | about 20 s |
| On-screen text | about 60 s |
| Re-encode + remux | about 15 s |

Switching **Read on-screen text** off cuts the time to roughly a third. Expect
about 3x the clip duration end to end with everything on.

## Troubleshooting

- **A curse word was missed in speech.** `tiny.en` is the weakest model. Switch to
  `base.en` in Settings, which is much better on accents and slang. If the speaker is
  quiet, lower `vad_threshold` toward `0.15`.
- **A subtitle was not blurred.** Raise `ocr_fps`, or widen `ocr_band` if the text is
  not near the bottom (`--ocr-band 0.9` scans nearly the whole frame). Stylised,
  moving or mid-fading subtitles are the hardest case.
- **A blurred caption is still readable.** That used to happen above 720p, because
  the blur strength was a fixed pixel radius. It is now proportional to the caption
  size, and `tests/test_blur_strength.py` fails if a caption survives the effect at
  either 360p or 1080x1920.
- **Something was beeped that should not have been.** Add the word to `allow` in the
  browser and save.
- **A job failed.** The traceback is in `work/<job id>/error.txt`.
- **Out of memory.** Close other programs, lower `max_resolution`, or turn off
  on-screen text. This machine has limited free RAM.

## Layout

```
app/live.py         the live filter: windowed, bounded delay, RTMP or local
app/profanity.py   word normalisation and matching
app/audio.py       beep synthesis and splicing
app/video.py       PyAV decode/encode/remux, blur and pixelate
app/ocr.py         RapidOCR pass and box tracking over time
app/pipeline.py    stage order and reporting
app/jobs.py        one job at a time, progress, cancellation
app/main.py        HTTP API
web/index.html     the page
data/              word list and settings
work/              uploads and per-job output, safe to delete
```

`run.sh` clears `PYTHONPATH` before starting, because the ROS entries on this
machine's `PYTHONPATH` break Python's plugin loading.

- **Live falls behind on this machine.** See the live section above. Use
  `--no-speech` and 360p, or run it somewhere with a GPU.
- **RTMP has not been tested end to end**, because there is no stream to point it
  at here. The protocol is supported by the bundled FFmpeg and the code path is
  the same one the local tests exercise, but treat the first real run as untested.
